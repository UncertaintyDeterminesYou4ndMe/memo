# Claude Code 自动记忆机制解析

## 背景

想弄清 Claude Code 是怎么管理"全局记忆"和"项目记忆"的。方法不是读文档，而是直接看本机 `~/.claude/` 下的实际文件：36 个项目桶、117 条记忆文件，再挑一条记忆顺着 `originSessionId` 找回原始会话记录，对比"对话里发生了什么"和"最后写进去了什么"。

---

## 第一个判断：没有"全局记忆"，只有"家目录这个桶"

一开始的提问前提就错了。Claude Code 有两套互不相干的东西，容易混：

| | CLAUDE.md | 自动记忆 memory/ |
|---|---|---|
| 谁写 | 人手写 | Claude 在对话中自己写 |
| 内容 | 工作原则、规范，"怎么做" | 用户是谁、纠正过什么、项目状态、外部链接 |
| 全局层 | `~/.claude/CLAUDE.md` | **没有** |
| 项目层 | 仓库里的 `CLAUDE.md` | `~/.claude/projects/<路径编码>/memory/` |
| 加载 | 每次会话全文注入 | 只注入索引，正文按需读 |

自动记忆按**启动目录**分桶，目录名是把 cwd 的 `/` 换成 `-`。在家目录启动 claude 时看到的"全局记忆"，其实只是 `-Users-<me>/memory/` 这一个桶。同一台机器上另外 35 个桶在这次会话里完全不可见。

两个直接后果：
- 在 `~/code` 和 `~/code/some-repo` 里启动是两个桶。同一条项目记忆在两个桶里各存了一份，就是这么来的。
- scratchpad 临时目录也会被建出空的 memory 桶，属于噪声。

想要真正跨项目的记忆，目前只有一条路：手写进全局 CLAUDE.md。代价是它从"按需召回的事实"变成"每次全文注入的指令"。

---

## 结构：四层

### 存储位置

```
~/.claude/
├── CLAUDE.md                      ← 手写全局指令（不是记忆）
└── projects/
    └── -Users-<me>-code-foo/      ← 目录名 = 启动路径
        ├── <sessionId>.jsonl      ← 会话原始记录（记忆的原材料）
        └── memory/
            ├── MEMORY.md          ← 索引，每次会话必注入
            └── <slug>.md          ← 一条记忆一个文件，按需读
```

记忆和会话记录在同一个桶里，靠 `originSessionId` 互相指向。

### 单条记忆 schema

```yaml
---
name: <slug>                      # 模型写
description: 一句话摘要             # 模型写：召回时判断相关性的唯一依据
metadata:
  type: project                   # 模型写：user / feedback / project / reference
  node_type: memory               # harness 补
  originSessionId: <uuid>         # harness 补
  modified: <ISO 时间>             # harness 补
---
正文。feedback / project 类要求带 **Why:** 和 **How to apply:**。
可用 [[其他记忆的 name]] 互链。
```

**字段分两个作者**，这是从会话记录里对出来的：首次 Write 的原文只有 `name`、`description`、`metadata.type` 三项，文件里多出的三项是写入后 harness 追加的。模型负责语义，harness 负责溯源。

117 条里 frontmatter 有 5 种变体，最老的 4 条连 `metadata` 块都没有。schema 改过至少两次，旧文件没迁移。

### 索引格式

一行一条：`- [标题](文件名) — 钩子`。26 个桶里 25 个平铺，1 个按 type 分节。钩子是**覆盖式**更新，只反映最新结论。

### 生命周期

- **召回**：会话开始时 harness 只把 MEMORY.md 注入 system prompt。正文不注入，模型觉得相关时自己 Read。所以 description 和索引钩子的质量直接决定召回率。
- **写入**：没有自动触发器，模型在对话中自己判断。规则给的判据：值得跨会话保留、仓库和 git 里查不到、不是只对本次对话有用。写前要求先查有没有已覆盖的文件。
- **更新**：实际操作序列是 `cat 读旧文件 → Edit 追加正文 → sed 覆盖索引行`。全是普通文件操作，没有专用记忆 API。

## 追溯一条记忆的三次写入：Claude 实际是怎么"总结"的

选了一条跨两个会话、写了三次的项目记忆（个人交易数据分析项目），把每次写入和会话记录对齐：

| 动作 | 触发 | 原始材料 | 写入量 |
|---|---|---|---|
| Write 新建 | 无人要求。"数据全部到齐，总账算完了。先存一条项目记忆，然后给你完整报告" | 会话记录 605KB，37 次 Bash 计算 | ~1.0KB |
| Edit 替换末段 | 无人要求。"最后一块拼图到位了。先更新记忆，然后给你综合诊断" | 用户一句话纠正 + 一轮计算 | ~1.2KB |
| cat → Edit 追加 → sed 改索引 | 无人要求。"全部算完。先更正我上一轮的推测……算出来是反的" | 全会话 assistant 文字 11K 字符 | ~1.3KB |

观察到的习惯：

**写的时机固定在"算完、报告前"**。三次都不是会话末尾，而是拿到结论那一刻，先写记忆再对用户输出。此时数据还在上下文里，不会因为后续压缩而失真。这是一种防丢失设计。

**保留什么很一致**：带样本量和统计量的数字、用户确认过的事实、用户给的硬约束、下一步方向。丢掉的：计算过程、脚本、中间假设、解释性文字。605KB 压到 1KB，约 600 倍。

**对错误猜测，第一次是删、第二次是留**。v1 里有一段"该账户可能不是主力"的推测，用户否定后被整段替换，不留痕迹。但第三次写入时，新结论直接推翻了第一次的一个论断，它没回去改旧段，只在末尾追加。结果是文件正文前后矛盾，索引行倒是改成了最新结论。

**索引覆盖、正文追加，这个不对称是有意的**。索引每次必读只留最新；正文按需读可以留历史。代价是正文越长，按需读的成本越高。

## 规则和实际执行的差距

| 规则 | 实际（117 条） |
|---|---|
| feedback / project 类带 Why + How to apply | 这两类 103 条，带齐 54 条 |
| 一个文件一个事实 | 26 条 >2KB，最大 14.8KB，78 条正文带日期段落，已是日志形态 |
| `[[链接]]` 互联 | 共 111 个链接，有在用 |
| 先查重再写 | 同桶内能查，跨桶查不到 |

type 分布：project 77、feedback 26、reference 10、user 4。project 占三分之二，这套记忆实际主要在当"项目状态板"，不是在积累对用户个人的了解。

## 关键知识点

1. **替换和追加是两种不同的记忆更新语义**。替换适合"猜测被事实推翻"，追加适合"新增一个阶段的结论"。选错的结果是文件内部矛盾，下次召回时模型要自己判断哪句对。这是目前机制里没有约束的一个点。
2. **两层加载（索引必读 + 正文按需）是核心设计决策**，和 skill 的 description + SKILL.md、CLAUDE.md + rules 目录是同一个模式在三处复用。
3. **"在哪个目录启动"是个有后果的决定**。桶按 cwd 划分，不按 git 仓库。
4. **harness 补字段意味着记忆有模型层和系统层两个作者**。以后做审计或过期清理，依据系统层字段（originSessionId、modified），不能指望模型自己写对时间。
5. **追溯方法可复用**：记忆文件 frontmatter 的 `originSessionId` → 同桶下的 `<id>.jsonl` → 过滤 `type=assistant` 且 tool_use 路径含 `memory/` 的行 → 往前找该 assistant 的最后一段 text 就是触发语句。
