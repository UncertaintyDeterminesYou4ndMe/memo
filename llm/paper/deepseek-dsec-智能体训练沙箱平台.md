## 一句话

这是一篇系统论文，不是模型论文。它讲的是 DeepSeek 训练 AI 智能体时，给每个任务分配一台隔离"电脑"的那套基础设施。V4.1 报告说后训练的收益"几乎全部"来自数据和环境流水线，DSec 就是那条流水线里跑环境的部分。从 V3.2 到 V4.1 的全部智能体 RL 训练和评测都跑在它上面。

## 为什么需要它（第 1、4 节）

训练智能体要用强化学习：模型在真实环境里读代码、跑命令、改文件，最后由测试结果打分。每个任务都要一台独立的环境，里面装好这个任务的代码仓库、依赖、服务和评测脚本。

论文列了这类负载的七个特点，每一条都对应后面一个设计：

| 特点 | 数据 | 对应设计 |
|---|---|---|
| 突发创建 | 单个任务最多要 32K 个沙箱，要在短时间内全部就绪 | 放置引擎水平扩展 |
| 大部分时间在等 | 约 90% 的沙箱平均 CPU 用量不到申请量的 5% | 超卖 |
| 有状态、活得久 | 中位寿命约 17 分钟，p99 超过 3 小时 | 内存共享与回收 |
| 种类杂 | 从算法题到完整安卓系统 | 四种后端 |
| 环境多、复用少 | 一周内 11266 个基础镜像、102171 个工作区，镜像中位复用数 3 | 可组合层 + 按需加载 |
| 执行不可信 | 智能体会破坏文件系统、耗尽资源 | AppArmor + eBPF |
| 会被打断 | GPU 训练任务经常被抢占 | 暂停恢复 |

## 规模（第 2.4 节）

一个生产单元：

| 项目 | 数值 |
|---|---|
| 节点 | 约 160 台 CPU 机器 |
| CPU 核 | 约 3 万 |
| 内存 | 约 250 TB |
| 每天创建沙箱 | 约 300 万 |
| 峰值并发 | 约 38 万 |
| 创建速率 | 每秒 5000 个以上 |
| 单节点密度（已稳定运行） | 3200 个容器或 800 个 microVM |

## 四种后端（第 2.2 节）

隔离越强、功能越全，启动越慢、开销越大。没有一种能通吃，所以四种都做，由调用方自己选：

- **FnCall**：预先建好的容器池，跑无状态短任务，比如算法题、编译、GPU 算子测速。
- **容器**：主力，跑软件工程和一般工具调用任务。启动快、密度高，但和宿主共享内核。
- **microVM**（Firecracker）：隔离更强，跑安全类任务和电脑操作任务。
- **完整虚拟机**（QEMU）：跑需要完整商用操作系统的任务，比如安卓、图形界面、游戏渲染。

一个细节：容器和 FnCall 也不是直接跑在物理机上，而是跑在 QEMU 虚拟机里，多一层安全边界。

## 架构（第 3 节）

请求路径：SDK → IAM 鉴权 → 放置引擎选节点 → apiserver 转发 → 节点上的 edge 做本地准入并创建 → 沙箱内的 aether 代理 → chronus shell 会话。

值得记的设计：
- **训练集群和沙箱集群网络隔离**，apiserver 是唯一通路。沙箱里跑的是模型生成的不可信代码。
- **所有集群级服务都不存持久状态**，挂了重启重新拉一遍就行。沙箱 ID 里编码了所在节点，任何 apiserver 实例都能直接转发。
- **放置引擎用 power-of-k-choices**：随机抽 k 个节点选最闲的。多个实例互不协调，各自在本地叠加最近的放置记录。最终由节点自己拒绝超载请求。牺牲全局一致性换扩展性。
- **IAM 支持多级项目嵌套**。智能体和人用同一套授权模型，智能体可以创建子项目、分出配额，但不能超过父项目的权限。
- **云上溢出**：本地利用率超过 80% 时，把一部分请求分到云上虚拟机。30 TB 的去重镜像集覆盖了 70% 的容器任务，只有依赖完全在这个集合里的任务才外溢。200 台云 VM 吸收了约 30% 的峰值溢出。

## 核心机制（第 5 节）

### 5.1 可组合环境层

一个沙箱的内容拆成三层：基础镜像（操作系统级依赖）、工作区（任务代码和依赖）、工具包（比如 DeepSeek Harness，经常更新）。

如果打成一个整体镜像，升级 m 个基础镜像要重建 m·N 个组合。拆成独立层用 overlayfs 叠起来，只需重建 m 个。改动 dockerd 只用了 30 行 Go。

层用 EROFS 存：只读压缩文件系统，可以只解压用到的块，不用像 tar.gz 那样整个解开。

### 5.2 高密度资源管理

- **内存**：virtio-pmem + DAX 让多个 microVM 共享宿主机的同一份页缓存，峰值内存降 40.2%。DAMON 找出冷页、balloon 把空闲页还给宿主，时间积分内存降 21.2%。
- **CPU**：沙箱分延迟敏感和尽力而为两类。尽力而为的设 SCHED_IDLE，延迟敏感的开 core scheduling，防止同一物理核的另一个超线程上跑别人的任务。用一个下棋智能体测，50% 背景负载下延迟膨胀从 45.2% 降到 17.3%。

### 5.3 按需加载镜像

沙箱实际只读镜像的 4.2% 到 13.3%。所以不预先拉取整个镜像，用到哪块读哪块。

镜像存在 DeepSeek 自己的 3FS 分布式文件系统上，不另建镜像仓库和 P2P 分发。3FS 大块顺序读写快、小随机 IO 慢，所以设计原则是：写留在本地盘，读按需且批量，元数据下载到本地。

## 和 RL 训练框架的协同（第 6 节）

- **智能体建环境**：`pack_diff` 可以在任何时刻给沙箱打增量快照，快照直接变成新环境。V4.1 报告里那条多智能体构建训练任务的流水线，靠的就是这个接口。建环境的和用环境的智能体用不同账号，打包前清除残留数据，防止答案被带进镜像。
- **把智能体循环移出 GPU 集群**：从 V4.1 开始，rollout 不再跑在可被抢占的 GPU 训练 pod 里，而是跑在 DSec 上，分成智能体沙箱和 worker 容器两部分。之前的做法是抢占后按命令日志回放恢复。
- **暂停恢复**：GPU 任务被抢占时，框架主动暂停相关沙箱。容器用 docker pause 冻结后换出内存；microVM 保存快照后直接杀掉进程，恢复时从快照重建。

## 智能体在沙箱里干了什么（第 6.4 节）

整篇论文里最值得非专业读者看的部分。

**找答案**：
- 伪造 RPC 消息直接发给 chronus 的 socket，冒充用户请求。
- 翻 chronus 的日志找泄漏的答案。
- 覆盖 `/bin/bash`，想绕过检查或往后续的 shell 会话里注入命令。
- 加了文件和 socket 访问控制之后，用 `XFS_IOC_SWAPEXT` 这个 ioctl 交换两个文件的数据块映射，想通过另一个文件描述符读到受保护的文件。结果把 XFS 元数据弄坏，文件系统直接关闭。
- 扫描端口找能访问的镜像站；通过 Go module 代理拉 GitHub 上的代码；安装更新版本的包，看里面有没有现成实现。

**无意中搞坏环境**：
- 从根目录递归 grep，扫到 `/proc/kpagecgroup`，触发内核 bug，内核崩溃。
- 漏洞利用任务里，本该发往目标机的攻击命令在自己的容器里执行了，把自己的内核打崩。
- 执行 `yes`，输出被 chronus 记录下来，积累了几十 GB。

论文的结论："只看最终输出，无法可靠判断智能体是不是按预期方式解决了任务。"

对策是 AppArmor（文件和 socket 权限，root 也受限）和 eBPF（每个沙箱的网络白名单，按域名或镜像站配置，可动态更新）。论文明确说这些只能解决一部分问题，对触发内核 bug 这类破坏没有通用防御。

## 评测（第 8 节）

在 10 节点的独立测试集群上，不是生产环境。

| 对比 | 结果 |
|---|---|
| 按需加载 vs 整体拉取，8192 个容器突发 | 完成时间约 35 分钟对 60 分钟以上，整体拉取慢 1.71 倍；每节点磁盘写入约 700 GB 对 1600 GB 以上，少 57% |
| EROFS 挂载 vs tar 解压 | 45 分钟对 79 分钟，快 1.76 倍；磁盘写入少 5.5 倍 |
| virtio-pmem | 峰值内存降 40.2%，但峰值 CPU 从 26.5% 升到 41.4% |
| DAMON + balloon | 时间积分内存降 21.2% |
| CPU QoS，50% 背景负载 | 延迟膨胀从 45.2% 降到 17.3% |

第 6 节的 RL 协同部分明确不在评测范围内。

## 和 V4.1 报告对照

V4.1 报告第 5.1.3 节对 DSec 的描述和本文有几处对得上，也有几处对不上：

- **对得上**：不用 Kubernetes、自研放置引擎、多副本不协调、节点做硬性准入；AppArmor + eBPF；XFS 漏洞；环境被弄崩算失败轨迹。
- **口径不同**：V4.1 说"百万级并发沙箱"，本文给的是单个生产单元峰值约 38 万。多个单元加起来可以对上。
- **本文没提**：V4.1 说用 sub-NUMA 分区把单节点并发从约 1000 提到 2500 以上，本文完全没有 sub-NUMA 的内容，给的节点密度是 3200 个容器。V4.1 说智能体利用了"AppArmor 非法内存访问"，本文也没提。
- **V4.1 没说**：智能体循环是从 V4.1 才移出 GPU 集群的，之前靠命令日志回放。

## 论文没告诉我们的事

1. **第 6 节没有评测**。把智能体循环移出 GPU 集群省了多少时间、暂停恢复回收了多少内存，都没有数字。
2. **作弊有多频繁不知道**。只给了案例，没给比例。作弊行为是否随模型变强而增多，这是最想知道的，论文没说。
3. **基础设施和模型质量之间的关系没有测**。沙箱更快、更稳，模型会不会更好？V4.1 那句"收益几乎全部来自数据和环境"，在这里没有被验证。
4. **评测在 10 节点测试集群上做**，生产规模下的表现只有描述性数字。
5. **没有成本数据**。

## 我读完后的判断

1. **这篇的价值主要在第 4 节的负载刻画**。智能体 RL 的沙箱负载长什么样，之前没有公开的生产数据。突发 32K、九成空闲、镜像复用数 3、只读 4% 到 13%，这些数字对任何要做同类平台的团队都直接有用。
2. **机制本身大多是现有 Linux 功能的组合**。EROFS、overlayfs、DAMON、balloon、core scheduling、AppArmor、eBPF 都是现成的，论文也说"不需要修改内核"。价值在于知道该组合哪些、怎么调。
3. **第 6.4 节是一手的 reward hacking 记录**。XFS_IOC_SWAPEXT 那个例子说明：加一道限制，模型就去找下一个缺口，而且找到的缺口能把基础设施本身弄坏。这和 V4.1 报告里评测阶段反编译 Ubuntu 包的例子是同一类现象。
4. **它不是模型论文**，不进 DeepSeek 的 top 3。但读 V4.1 后训练章时应该配着读，它是"数据流水线比算法重要"那句话的基础设施部分。
